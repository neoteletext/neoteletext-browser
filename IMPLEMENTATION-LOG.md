# Implementation log

The questions met while implementing without the owner, and the answer taken, as `~/devel/neoteletext-common/DEVELOPMENT.md` section 3.3 asks: number, question, decision, reason. A row is amended in place or superseded by a later row that says so. Rows are numbered within each section; a reference to a row of "Installer and updater" names that section. Behaviour the standard leaves open is a decision (`docs/architecture.md` section 2), not a row here.

| 17 | How does the harness reach the core, when random bytes are almost all refused? | It learns from the protocol's reader which lengths each kind takes, fills them with arbitrary values, and mutates real messages. | Learning from the reader cannot drift from it; 8,000 to 9,000 of the 30,000 messages reach the core. |
| 18 | Damage-limited drawing: change the presentation library, or limit what is drawn with the libraries in the tree? | The libraries in the tree: the painter keeps the calls, compares them with the last frame's, and draws only the boxes that changed; the surface is told the boxes. | A new library is an architectural decision for the owner (rule 2.1); the present on macOS stays a whole copy, recorded in `TECH-DEBT.md`. |

| 21 | Keep web addresses from another browser? | Those the address rules accept, as a typed bookmark's are; `place:`, `javascript:`, `data:` and the rest are left out and counted. | A bookmark here is a channel; the rules already decide what can be opened. |

## Installer and updater

Building decision 54 (`docs/installation-and-updates.md`) on every desktop, 23 October 2026, while the owner was away, as the owner instructed: "do everything, do not stop, make the decisions you need". The decisions are 73 to 82 in `docs/architecture.md` section 2, in a block of their own.

| 1 | `tough` brings `rustls` with its default features, which turn on a second cryptography provider in every crate of the workspace; the fetcher's and the engine's qrkeyboard client's `ClientConfig::builder()` then panic. Change those call sites, or keep `tough` apart? | A workspace of its own, `native/tuf`, for the updater and the release tool, with its own lockfile, `deny.toml` and fuzz targets; the gates run it beside the browser's (decision 73 item 1). | The engine's client cannot be changed here (requirement 2.5); keeping `tough`'s 136 crates out of the browser's build also keeps them out of every other process and gate. |
| 2 | Which library for The Update Framework, now that `tough` is async and built on `aws-lc-rs` (design section 8.2)? | `tough` 0.24.0, as decision 24 and the owner's answer 2 kept it, with `tokio` on one thread; checked by `cargo deny`: every licence permitted (decision 74). | Its weight sits in one confined process that holds no platform key; it built on all three desktops without `cmake` or `nasm`. |
| 3 | The design names `miniz_oxide` "already in the browser through the PNG reader", which decision 61 removed. | `miniz_oxide` 0.9.1, named directly, with gzip's framing and CRC-32 written to RFC 1952 in `update::gzip` (decision 74). | A strict reader of only what the release tool writes is smaller than a general gzip crate. |
| 4 | Exchanging two folders needs `renamex_np` and `renameat2`, which `libc` reaches only with unsafe code. | `rustix` 1.1.5, already under `winit` and `tempfile`, named directly: `renameat_with(..., RenameFlags::EXCHANGE)` on both, and the process group of a hung trial ended through it (decision 74). | A safe interface; no new crate in the tree. |
| 5 | The launcher on macOS has no window but must offer to move a translocated bundle; Windows needs `WinVerifyTrust`, the registry and a message box. Requirement 10.12 allows unsafe code only in three crates. | A fourth, `os-install`, with unsafe code only in its `macos.rs` (CoreFoundation's `CFUserNotificationDisplayAlert`) and `windows.rs`; requirement 10.12 amended (decision 75). `confine`'s Windows module gains the grant to `ALL APPLICATION PACKAGES` and the containers' removal, under its existing permission. | The brief asked for unsafe calls to be kept in a small crate of their own. |
| 6 | How do tests use test keys and a local host without a switch a user's machine could turn (decision 58)? | The release's identity is built in at build time (`native/release-identity`), from `production/` or a test identity's folder; nothing reads it at run time. | 7 | Where do macOS's `state` and `staging` go, given the confined core may write `~/Library/Application Support/NeoTeletext`? | `~/Library/Application Support/NeoTeletext Updates/` (decision 79). | Only the launcher may write the state; only the updater the staging folder. |

| 10 | What is "the interface has drawn its first frame"? | `ToCore::Drawn`, sent once after the first frame reaches the screen; with the settings read and no decoder ended in error, within 30 seconds and 2 seconds settled (decision 80). | A restored web channel may be offline, so a page cannot be required. |
| 11 | How is a version read "from inside the signed files" on macOS and Windows? | A version mark in the broker's bytes, `\x01neoteletext-version\x01<v>\x01`, found by one bounded search (decision 80). | No property-list or resource reader; the same on both. |
| 12 | Should the updater write the targets metadata beside a staged version (section 3.1 step 3)? | No: the release's manifest, itself a target, is written there; The Update Framework's trusted metadata stays in `staging/metadata/`, the datastore that stops rollbacks. | Nothing would read the targets metadata there. |
| 13 | The strip's offer: a button in the strip? | A notice, once ("NeoTeletext 0.3 is available: Install it in Settings"); "Install" is in the settings panel with the version and the trusted core's line about updates (decision 81). | The strip's address field stays the channel's; the panel is where settings act. |

| 16 | Windows packaging: `ALL APPLICATION PACKAGES`, the containers' profiles, a fetcher's loopback exemption, the interface's container. | The installer grants read and execute on `versions\` with no administrator; the profiles are made at first start and removed at uninstall; the loopback exemption needs an administrator and is not given; the interface keeps its restricted token (decision 78). | What needs an administrator is said, never done by a per-user installer. |
| 17 | The uninstaller cannot remove itself while running on Windows. | A copy in `%TEMP%` does the removal once the launcher has ended, and stays there (decision 82). | `MoveFileEx`'s delayed delete needs an administrator. |

### Status, 23 October 2026

**Done and verified.** The launcher, the stub, the Windows installer, the confined updater, the release tool and the browser's side of updates, on macOS, Linux and Windows (decisions 73 to 82). Each platform's tests pass (launcher, updater and release tool, the updater's probe on Linux), the fuzz targets of every new reader ran clean, and each platform's end-to-end test passed: install, a healthy start, an update staged by the confined updater and committed, a crashing release rolled back, a release not signed by the pinned signer refused, removal; on macOS and Linux also expired metadata and a full disk, and on Linux a launcher release. The AppArmor profile was proven on the Linux host with the restriction on. The details are `docs/installation-and-updates.md` section 15.
