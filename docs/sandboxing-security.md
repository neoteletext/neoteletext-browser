# Sandboxing: security analysis

The analysis of [`sandboxing.md`](sandboxing.md), as `DEVELOPMENT.md` section 2.3 asks of a feature that adds inputs, outputs or dependencies. It extends [`security-analysis.md`](security-analysis.md); its findings are in that document's sections 5.1, 5.3, 5.5, 5.7, 5.8, 13 and 16.

## 1. What the sandboxes protect

The property of decision 20: a compromised helper, by a fault in a reader of untrusted data or in a dependency, gains nothing beyond its pipe. Concretely, a compromised decoder must not read the user's files, reach the network or start a program; a compromised fetcher must not read the user's files or start a program, and reaches only the network, which it had; a compromised interface must not reach the network or files beyond fonts and preferences, and must not start a program; a compromised sound helper reaches the sound output and nothing else; a compromised trusted core must not reach the network, the user's files beyond its settings and those the user gave (REQ-1698), or start any program but the browser's own helpers, each confined by the broker (decisions 55 and 56).

## 2. Threats to the sandboxes themselves

Local files (`sandboxing.md` section 7.6) add three inputs to the broker, the one process not confined: the interface's channel, the chooser's output, and the single-instance channel. Each is bounded. The first and third are fuzzed, and what they name is still put through decision 88's checks. The chooser runs unconfined and is believed only for one absolute path, which is read as any other. On Linux the broker also asks the chooser, once at its start, for the desktop portal's reduced-motion preference (DEC-2424): at most eight bytes of its output are read, and only the one fixed answer from a chooser that ended well means reduced motion; the broker parses no D-Bus, and the interface, told by one variable of the environment the broker builds for it, still reaches no session bus (decision 86).

| Threat | Where | Control |
|---|---|---|
| A layer is missing on the user's machine | Linux | Every layer is required (decision 58): without the namespace, Landlock 5 enforced whole, or a filter for the architecture, the process ends with its reason and the browser does not run. Tested: `a_helper_without_its_namespace_does_not_run`, `a_file_to_read_keeps_landlock_whole`. |
| A new C library release uses a system call the filter does not expect | Linux | A deny-list: new calls pass; only named dangerous classes are refused. The cost is a weaker filter than an allow-list; the gain is a browser that keeps running. |
| The filter is applied after a thread exists, leaving that thread unconfined (the engine's `neottx` has this gap) | Linux | `confine::apply` is the first call of each helper's `main`. |
| `clone3`, whose flags the filter cannot read, starts a process | Linux | Answered "not implemented", so the C library falls back to `clone`, which the filter inspects for `CLONE_THREAD`. |
| An `AF_UNIX` socket reaches a service the helper should not: the session bus, where systemd starts any program unconfined, the system bus, an agent's socket | Linux | Controlled since decision 86 (`sandboxing.md` section 9.1); before, any helper allowed `AF_UNIX` could reach them, since Landlock does not control `connect` and the service's own access control lets the same user do anything. A decoder and the trusted core may open no socket at all; the fetcher, the phone keyboard and the updater no local socket, and of netlink only routing; the interface and the sound helper find in their own `/run`, `/tmp` and runtime folder only their display's or sound server's sockets. No helper may copy another process's descriptor (`pidfd_getfd`). Tested: `a_network_helper_reaches_no_local_socket`, `the_interface_reaches_its_display_and_no_bus`, `the_sound_helper_reaches_its_server_and_no_bus`, `no_helper_takes_another_process_descriptor`. |
| A compromised fetcher or phone keyboard reaches this computer's services or the local network, which only the engine's check inside it refuses (requirement 5.10) | macOS, Linux | macOS: the fetcher's profile refuses `localhost` unless the channel may reach the local network (decision 89; tested: `a_fetcher_reaches_this_computer_only_when_allowed`, which connected on the code before); the profile language cannot name private ranges, so the local network beyond this computer is a residual. Linux: a residual on both, held by the fetcher's own check alone; connecting in the broker is the planned design. Windows: an AppContainer reaches loopback only with an exemption, which none has. |
| The interface or sound helper reads another application's per-user cache, or the interface opens a URL through LaunchServices | macOS | The system reads are narrowed to this program's own `DARWIN_USER_CACHE_DIR` and `DARWIN_USER_TEMP_DIR`, not all of `/private/var/folders` (finding F-52; tested: `the_system_reads_name_only_this_user_s_folders`, and a `sandbox-exec` probe denies a foreign folder). The interface keeps `launchservicesd`, measured as needed to draw the window; whether it can open a URL through it is an unmeasured residual, left to the owner since denying the service stops the window. It also keeps `com.apple.coreservices.appleevents`, so it receives the quit Apple Event the Dock's Quit sends (28 October 2026); sending Apple Events to other applications stays denied by `(deny default)`, which covers `appleevent-send`, unmeasured under this profile. |
| A helper reads a path Landlock lets through | Linux | Read-only rules on system directories and, for the interface, fonts and preferences; nothing under the user's documents; nothing writable but `/dev/snd` for the sound helper and the settings folder for the trusted core. |
| The AppContainer cannot be made or started (for one, without the user's profile folders in the environment) | Windows | The process is not started, and the browser says why (decision 58); there is no weaker fallback and no switch to one. Tested: `a_helper_whose_container_cannot_be_made_is_not_started`, which failed on the code that fell back. |
| A handle the parent holds open is inherited | Windows | The handle list attribute: the two pipes, and a third for standard error when the broker has one, which the broker relays (decision 100 item 1), and nothing else. The broker duplicates a helper's pipe handles into the core's process one by one, with the same access, and closes its own. |
| A compromised trusted core asks the broker for a program, role or file it should not have | All | It names one of five helpers, never a path or a role; the broker reads a file channel by the channel rules, only teletext (or an import's bookmarks file), never beneath a dot-entry of the home folder, applications' data or the browser's own folders, and never through a link, opened by descriptor (decision 88); every request is bounded and fuzzed (`sandboxing.md` section 7, `security-analysis.md` section 5.8). |
| The trusted core's container fails to start | Windows | No core and no browser (decision 58). |
| A DLL the broker needs breaks the core's start under the Win32k filter | Windows | `shell32.dll` is delay-loaded in `neoteletext.exe` (`core/build.rs`); `the_trusted_core_starts_confined_and_reaches_its_own_code` starts the core confined on every platform. |
| The helper outlives a crashed trusted core or broker | All | Windows: the job's kill-on-close; the core's end closes the job. Linux: each helper is killed when its parent, the broker, ends, however it ends (`PR_SET_PDEATHSIG`, finding F-34; tested: `a_helper_ends_with_its_broker`). macOS: the helper ends at its pipe's end. |
| A helper reads the user's files or reaches the network at low integrity | Windows | Low integrity denies writes, not reads or Winsock; reads and the network are denied by the AppContainer, which every helper has since decision 90, the interface with no capabilities (`sandboxing.md` section 9.2). Before, the interface ran under a restricted token alone and could read the user's files and send them out. Built; `the_interface_reaches_no_network_and_no_user_file` passed in the virtual machine on 24 October 2026 and failed on the code before; the window working in its container is still to be checked there by hand. |
| A helper types into the console the browser was started from | Windows | Every helper starts detached from any console (`DETACHED_PROCESS`), and `AttachConsole` to its parent or the shell is refused across the container boundary (measured); its standard error is a pipe the broker relays a line at a time without control characters, so no terminal request (`ESC [6n`, whose answer a terminal types into its own input) reaches a terminal the broker's standard error leads to (decision 100 item 1, `sandboxing.md` section 9.10). Tested: `a_confined_helper_cannot_type_into_its_console` failed on the code before in the virtual machine's desktop session, where every role wrote its key events into the console, and passes now. On Linux seccomp refuses `TIOCSTI` and `TIOCLINUX` (finding F-22). |
| A link in the core's settings folder carries the folder's grant elsewhere | Windows | Measured, not so (finding F-70, TODO-2202, 4 November 2026): the broker grants the core's container its settings folder with an inheritable entry (`SetNamedSecurityInfoW`) at every start. In the Windows 11 virtual machine (build 26200), with a junction in the settings folder to `%USERPROFILE%\Documents` and another to a folder in it holding a file, a start of the browser left `Documents`, that folder and the file with no AppContainer entry: the propagation does not follow a junction. The grant therefore stays at start; had an entry appeared, it would have moved to install time on a handle, with a protected list and no propagation (`SetSecurityInfo`). |
| A helper inherits a descriptor of the broker's that it was not given: one another broker thread makes while the helper starts, or one a system library leaves without close-on-exec | macOS, Linux | Reviewed on 3 November 2026 (TODO-1994), section 6. On macOS a socket, pipe or accepted connection is made close-on-exec in a second system call, and while the broker's serving thread started a helper, its single-instance thread accepted connections and its file dialog's thread made a pipe: a helper started between the two calls held that descriptor for its whole life, which could give a compromised helper a second start's opening, or the write end of the file dialog's output, through which it could name a file as if the user had chosen it. Since then every program the broker starts on macOS, helper or trusted core, has every descriptor but its standard input, output and error, and the interface's channel, made close-on-exec in the child before it runs (`hold_only` in `confine/src/unix/descriptors.rs`), as `POSIX_SPAWN_CLOEXEC_DEFAULT` would. Tested: `a_helper_holds_only_its_own_descriptors_while_others_are_made` (19 of 100 starts held a stray descriptor on the code before) and `a_descriptor_left_inheritable_does_not_reach_a_helper` (given it on the code before). Linux makes the standard library's descriptors close-on-exec atomically, so a residual there is only a library's descriptor left without the flag. |
| `sandbox-exec` is deprecated and goes away | macOS | Still present on macOS 15; packaging must keep each process under a profile of its own (requirement 3.8). |
| The environment carries the user's secrets or tokens to a helper | All | `env_clear` with an allow-list: nothing for a decoder, fetcher or keyboard beyond what Windows needs to start a process; the window system's variables for the interface. |
| The report lies, because a compromised helper prints it | All | The report is for the user's information; nothing decides on it. |

## 3. What each platform's sandbox does not stop

- **Linux:** a fault in the kernel; for the interface and the sound helper, a fault in the display server or the sound server they still reach, and a local socket outside `/run`, `/tmp` and the runtime folder, which none of the usual services keep.
- **Windows:** a fault in the kernel or in a service a container may still reach; for the interface, whether an input method's composition, a change of display scaling and the pointer's shapes work in its container (decision 90), still to be seen by hand in the virtual machine (TODO-2200): its window was seen by script on 4 November 2026 to open, draw a page and the strip, take typing and the clipboard, resize, maximise and enter and leave full screen there. A junction swapped in for a folder of a file channel's path after the broker resolved it is no longer a residual: the broker compares the opened handle's final path with the path it opened (`d311650`, decision 88), and `a_junction_inside_the_path_refuses_the_open` passed in the virtual machine on 4 November 2026 and failed there with that comparison taken out.
- **macOS:** whatever `system.sb` allows every process, which Apple maintains.
- **All:** a fault in the broker's parser, the one process not confined (`security-analysis.md` section 5.8); a compromised trusted core still holds the browser's state and draws nothing but can mislead through what it sends the interface (`security-analysis.md` rank 4).

## 5. Remaining risk

Low on macOS and Linux for the helpers and the trusted core; low for the broker, small and parsing only the core's bounded requests; low for the interface on Windows, whose container's refusals were verified in the virtual machine on 24 October 2026, its window in the container still to be checked there.

## 6. Review: descriptors a helper could inherit (TODO-1994, 3 November 2026)

The question: on macOS, can a confined helper hold a descriptor the broker opens on another thread while it starts that helper? Every confined process is started by the broker (`confine::broker::serve`, on the broker's main thread, through `spawn` and `start_core` in `confine/src/unix.rs`); nothing else in the browser starts a confined process. The trusted core receives descriptors (`recvmsg`, made close-on-exec in a second call on macOS) but starts no program, so its own non-atomic step reaches no one.

The broker's threads that make descriptors on macOS, beside the one that starts helpers:

1. **The single-instance listener** (`listen` in `core/src/broker.rs`): each `accept` of a second start's connection. A helper holding it could read what the second start sends, a link and file names, which the browser would then not open, or keep that start waiting.
2. **The file dialog's thread** (`Chooser::start` in `core/src/broker.rs`): the pipe of the dialog's standard output, made when the dialog starts. A helper holding the write end could write a path, which the broker would take as the user's choice and grant the trusted core (decision 88); and the broker's read would not end until that helper ended.
3. **The interface's declaration thread** (`hear_declarations` in `confine/src/broker/server.rs`) and its callback make no descriptor: they read and write a socket made before the helper was started.
4. **The system's own libraries**, on threads they start for the broker (LaunchServices for a web address, the Security framework for the cookie key): what they make is outside the browser's code, and a descriptor any of them leaves without close-on-exec, at any time, would be given to every helper started after.

Measured on the Mac on the code before: with two threads making socket pairs and pipes, 19 of 100 decoders started held one or two descriptors that were not theirs; a descriptor the test left without close-on-exec reached every helper. So the first two give a compromised helper something its profile denies it, the second a grant of the user's files, though only when its start falls in a window of microseconds that a compromised trusted core could try to widen by asking for helpers while a dialog opens.

The remedy chosen (DEC-2345): in the child, after the fork and before `sandbox-exec` runs, every descriptor from 3 up to the size of the descriptor table is made close-on-exec except the interface's channel, so the helper holds its standard input, output and error, that channel, and what it opens itself. It closes both the race and the library residual, needs no change to the broker's other threads, and keeps the standard library's `Command` and `Child`. `POSIX_SPAWN_CLOEXEC_DEFAULT` would do the same in one call, but the standard library does not offer it, and calling `posix_spawn` directly would mean replacing `Child` with a process type of our own. A lock around every descriptor the broker makes was rejected: it cannot cover the system's libraries, and every new thread would have to remember it. A start takes the same time as before, about 21 milliseconds for a decoder on the Mac (101 starts in 2.11 seconds before and after).

Linux is unchanged: the standard library passes `SOCK_CLOEXEC`, `pipe2` and `accept4` there, atomically, and its `Command` uses `posix_spawn` unless a start needs code in the child. The residual there is a library's descriptor left without close-on-exec in the broker, of which none is known.

The other direction, a helper's pipes held by the unconfined file dialog when the dialog starts while a helper's pipes exist, gives the dialog nothing it lacks, as it is not confined; it can only delay the end of that helper's input until the dialog closes.
