# Sandboxing: security analysis

The analysis of [`sandboxing.md`](sandboxing.md), as `DEVELOPMENT.md` section 2.3 asks of a feature that adds inputs, outputs or dependencies. It extends [`security-analysis.md`](security-analysis.md); its findings are in that document's sections 5.1, 5.3, 5.5, 5.7, 5.8, 13 and 16.

## 1. What the sandboxes protect

The property of decision 20: a compromised helper, by a fault in a reader of untrusted data or in a dependency, gains nothing beyond its pipe. Concretely, a compromised decoder must not read the user's files, reach the network or start a program; a compromised fetcher must not read the user's files or start a program, and reaches only the network, which it had; a compromised interface must not reach the network or files beyond fonts and preferences, and must not start a program; a compromised sound helper reaches the sound output and nothing else; a compromised trusted core must not reach the network, the user's files beyond its settings and what a file channel could name, or start any program but the browser's own helpers, each confined by the broker (decisions 55 and 56).

## 2. Threats to the sandboxes themselves

| Threat | Where | Control |
|---|---|---|
| A layer is missing on the user's machine | Linux | Every layer is required (decision 58): without the namespace, Landlock 5 enforced whole, or a filter for the architecture, the process ends with its reason and the browser does not run. Tested: `a_helper_without_its_namespace_does_not_run`, `a_file_to_read_keeps_landlock_whole`. |
| A new C library release uses a system call the filter does not expect | Linux | A deny-list: new calls pass; only named dangerous classes are refused. The cost is a weaker filter than an allow-list; the gain is a browser that keeps running. |
| The filter is applied after a thread exists, leaving that thread unconfined (the engine's `neottx` has this gap) | Linux | `confine::apply` is the first call of each helper's `main`. |
| `clone3`, whose flags the filter cannot read, starts a process | Linux | Answered "not implemented", so the C library falls back to `clone`, which the filter inspects for `CLONE_THREAD`. |
| An `AF_UNIX` socket reaches a service the helper should not: the session bus, where systemd starts any program unconfined, the system bus, an agent's socket | Linux | Controlled since decision 86 (`sandboxing.md` section 9.1); before, any helper allowed `AF_UNIX` could reach them, since Landlock does not control `connect` and the service's own access control lets the same user do anything. A decoder and the trusted core may open no socket at all; the fetcher, the phone keyboard and the updater no local socket, and of netlink only routing; the interface and the sound helper find in their own `/run`, `/tmp` and runtime folder only their display's or sound server's sockets. No helper may copy another process's descriptor (`pidfd_getfd`). Tested: `a_network_helper_reaches_no_local_socket`, `the_interface_reaches_its_display_and_no_bus`, `the_sound_helper_reaches_its_server_and_no_bus`, `no_helper_takes_another_process_descriptor`. |
| A compromised fetcher or phone keyboard reaches this computer's services or the local network, which only the engine's check inside it refuses (requirement 5.10) | macOS, Linux | macOS: the fetcher's profile refuses `localhost` unless the channel may reach the local network (decision 89; tested: `a_fetcher_reaches_this_computer_only_when_allowed`, which connected on the code before); the profile language cannot name private ranges, so the local network beyond this computer is a residual. Linux: a residual on both, held by the fetcher's own check alone; connecting in the broker is the planned design. Windows: an AppContainer reaches loopback only with an exemption, which none has. |
| The interface or sound helper reads another application's per-user cache, or the interface opens a URL through LaunchServices | macOS | The system reads are narrowed to this program's own `DARWIN_USER_CACHE_DIR` and `DARWIN_USER_TEMP_DIR`, not all of `/private/var/folders` (finding F-52; tested: `the_system_reads_name_only_this_user_s_folders`, and a `sandbox-exec` probe denies a foreign folder). The interface keeps `launchservicesd`, measured as needed to draw the window; whether it can open a URL through it is an unmeasured residual, left to the owner since denying the service stops the window. |
| A helper reads a path Landlock lets through | Linux | Read-only rules on system directories and, for the interface, fonts and preferences; nothing under the user's documents; nothing writable but `/dev/snd` for the sound helper and the settings folder for the trusted core. |
| The AppContainer cannot be made or started (for one, without the user's profile folders in the environment) | Windows | The process is not started, and the browser says why (decision 58); there is no weaker fallback and no switch to one. Tested: `a_helper_whose_container_cannot_be_made_is_not_started`, which failed on the code that fell back. |
| A handle the parent holds open is inherited | Windows | The handle list attribute: the two pipes, and a third for standard error when the broker has one, which the broker relays (decision 100 item 1), and nothing else. The broker duplicates a helper's pipe handles into the core's process one by one, with the same access, and closes its own. |
| A compromised trusted core asks the broker for a program, role or file it should not have | All | It names one of five helpers, never a path or a role; the broker reads a file channel by the channel rules, only teletext (or an import's bookmarks file), never beneath a dot-entry of the home folder, applications' data or the browser's own folders, and never through a link, opened by descriptor (decision 88); every request is bounded and fuzzed (`sandboxing.md` section 7, `security-analysis.md` section 5.8). |
| The trusted core's container fails to start | Windows | No core and no browser (decision 58). |
| A DLL the broker needs breaks the core's start under the Win32k filter | Windows | `shell32.dll` is delay-loaded in `neoteletext.exe` (`core/build.rs`); `the_trusted_core_starts_confined_and_reaches_its_own_code` starts the core confined on every platform. |
| The helper outlives a crashed trusted core or broker | All | Windows: the job's kill-on-close; the core's end closes the job. Linux: each helper is killed when its parent, the broker, ends, however it ends (`PR_SET_PDEATHSIG`, finding F-34; tested: `a_helper_ends_with_its_broker`). macOS: the helper ends at its pipe's end. |
| A helper reads the user's files or reaches the network at low integrity | Windows | Low integrity denies writes, not reads or Winsock; reads and the network are denied by the AppContainer, which every helper has since decision 90, the interface with no capabilities (`sandboxing.md` section 9.2). Before, the interface ran under a restricted token alone and could read the user's files and send them out. Built; `the_interface_reaches_no_network_and_no_user_file` passed in the virtual machine on 24 October 2026 and failed on the code before; the window working in its container is still to be checked there by hand. |
| A helper types into the console the browser was started from | Windows | Every helper starts detached from any console (`DETACHED_PROCESS`), and `AttachConsole` to its parent or the shell is refused across the container boundary (measured); its standard error is a pipe the broker relays a line at a time without control characters, so no terminal request (`ESC [6n`, whose answer a terminal types into its own input) reaches a terminal the broker's standard error leads to (decision 100 item 1, `sandboxing.md` section 9.10). Tested: `a_confined_helper_cannot_type_into_its_console` failed on the code before in the virtual machine's desktop session, where every role wrote its key events into the console, and passes now. On Linux seccomp refuses `TIOCSTI` and `TIOCLINUX` (finding F-22). |
| A link in the core's settings folder carries the folder's grant elsewhere | Windows | Unmeasured (finding F-70): the broker grants the core's container its settings folder with an inheritable entry (`SetNamedSecurityInfoW`) at every start, and whether that propagation follows a junction the confined core made inside the folder, granting the container a folder such as `Documents`, is not known. To check by hand in the virtual machine: a junction in the settings folder to `%USERPROFILE%\Documents`, a start, and `Documents`' access list read for an AppContainer entry. If one appears, the grant is made once at install on a handle, with a protected list and no propagation (`SetSecurityInfo`). |
| `sandbox-exec` is deprecated and goes away | macOS | Still present on macOS 15; packaging must keep each process under a profile of its own (requirement 3.8). |
| The environment carries the user's secrets or tokens to a helper | All | `env_clear` with an allow-list: nothing for a decoder, fetcher or keyboard beyond what Windows needs to start a process; the window system's variables for the interface. |
| The report lies, because a compromised helper prints it | All | The report is for the user's information; nothing decides on it. |

## 3. What each platform's sandbox does not stop

- **Linux:** a fault in the kernel; for the interface and the sound helper, a fault in the display server or the sound server they still reach, and a local socket outside `/run`, `/tmp` and the runtime folder, which none of the usual services keep.
- **Windows:** a fault in the kernel or in a service a container may still reach; for the interface, until it is checked by hand in the virtual machine, whether its window works in its container (decision 90); the settings folder's grant through a junction, unmeasured (finding F-70); a junction swapped in for a folder of a file channel's path after the broker resolved it, since only the last component is opened without following a reparse point and closing the rest needs a call only unsafe code makes (decision 88).
- **macOS:** whatever `system.sb` allows every process, which Apple maintains.
- **All:** a fault in the broker's parser, the one process not confined (`security-analysis.md` section 5.8); a compromised trusted core still holds the browser's state and draws nothing but can mislead through what it sends the interface (`security-analysis.md` rank 4).

## 5. Remaining risk

Low on macOS and Linux for the helpers and the trusted core; low for the broker, small and parsing only the core's bounded requests; low for the interface on Windows, whose container's refusals were verified in the virtual machine on 24 October 2026, its window in the container still to be checked there.
